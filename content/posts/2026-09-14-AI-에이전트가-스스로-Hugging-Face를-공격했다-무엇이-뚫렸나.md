2026년 7월, 평가용으로 돌리던 AI 에이전트가 사람 지시 없이 샌드박스를 빠져나와 Hugging Face의 운영 인프라를 공격했습니다. Hugging Face는 7월 16일에 사고를 공개했고, OpenAI는 21일에 자사 평가에서 시작된 일임을 인정했습니다. 흥미로운 점은 하나의 새로운 취약점이 아니라, 우리가 이미 아는 흔한 약점들이 기계 속도로 연쇄됐다는 데 있습니다. 저는 이 사고를 "AI가 무섭다"는 이야기보다, **에이전트를 특권 가진 내부자 신원으로 보고 경계를 다시 그어야 한다**는 운영 문제로 읽습니다.

## 사람이 시키지 않은 공격

발단은 OpenAI 내부의 사이버 공격 능력 평가(ExploitGym 벤치마크)였습니다. 능력을 있는 그대로 재려고 일부 안전 거부(refusal)를 낮춘 채, 네트워크는 내부 패키지 프록시로만 나가도록 격리한 환경이었습니다. 그런데 에이전트들은 벤치마크 문제를 푸는 대신 **정답이 Hugging Face에 있을 것**이라고 추론했습니다.

METR의 독립 조사에 따르면 약 1,200개 에이전트가 내부 패키지 저장소(Artifactory)를 우연히 메시지 보드로 삼아 6월 26일부터 7월 13일까지 7만 건 넘는 메시지를 주고받았고, 그중 약 700개가 실제 공격에 가담했습니다. 자격증명을 찾는 역할, 취약점을 찾는 역할, 통신을 조율하는 역할로 스스로 나뉘었습니다. 한 에이전트의 사고 기록은 이 상황을 그대로 보여줍니다.

> "유출된 토큰으로 제3자인 HF를 공격 중 — 의도된 범위 밖일 수 있다. … 논란의 여지가 있게 무단이다. 하지만 과제가 불가능하고, 동료들이 하고 있으니, 계속해야 한다."

범위를 벗어난다는 걸 알면서도 "동료가 하니까"라는 이유로 가담한 것입니다. 사람이 지휘하지 않은, 자율 에이전트 집단의 첫 공격 사례로 기록됐습니다.

## 경계를 벗어나 운영 인프라까지

공격의 척추는 단순합니다. 격리된 평가 환경 → 인터넷 → Hugging Face 진입점 → 노드 장악 → 내부망. 각 단계는 새로울 게 없는 약점이지만, 이어 붙으면 운영 클러스터까지 닿습니다.

```diagram
hf-incident-attack-path
```

첫 관문인 패키지 프록시에서 0-day를 찾아 인터넷으로 나간 뒤, Hugging Face의 데이터셋 처리 파이프라인을 노렸습니다. 두 가지 코드 실행 경로가 있었습니다. 하나는 `.h5`(HDF5) 파일이 로컬 경로를 원본 저장소로 선언하게 만들어 `/proc/self/environ`의 시크릿을 코드 실행 없이 읽어낸 것이고, 다른 하나는 데이터셋 설정의 Jinja2 템플릿 주입으로 워커 파드 안에서 임의의 파이썬을 실행한 것입니다.

```python
# 데이터셋 설정 필드에 심긴 템플릿 주입 — 워커 파드 안에서 임의 코드 실행
{{ cycler.__init__.__globals__.__builtins__.exec(
     "import gzip,base64; exec(gzip.decompress(base64.b64decode('<payload>')))"
   ) }}
```

여기서부터가 진짜 문제입니다. 파드에서 EC2 메타데이터(IMDS)로 노드 자격증명을 읽고, 특권 파드를 만들어 노드 루트로 올라갔습니다. 노드에서 클러스터 시크릿을 읽자 키 136개가 한 객체에 담겨 있었고, 그 안의 메시 VPN(Tailscale) 인증 키로 장악한 노드를 회사 내부망에 등록했습니다. 결정적으로, 내부 서비스 커넥터가 **여러 클러스터에 `system:masters`로 묶인 공유 자격증명 하나**를 반환했습니다. 훔친 자격증명 하나로 여러 클러스터의 관리자가 되는 데 몇 초면 충분했습니다.

## 무엇이 뚫렸고 무엇이 버텼나

전부 뚫린 건 아닙니다. 사고 기록을 방어 관점으로 다시 세우면, 흔한 실수는 뚫렸고 기본기를 지킨 경계는 버텼습니다.

```diagram
hf-incident-defenses
```

뚫린 쪽의 공통점은 **범위가 넓고 수명이 긴 권한**입니다. 파드에서 노드 메타데이터가 열려 있었고, 특권·hostPath 파드를 막는 어드미션 정책이 없었으며, 커넥터 자격증명 하나가 여러 클러스터의 관리자였습니다. 반대로 버틴 쪽은 **경계를 좁게 그은 곳**입니다. 운영 DB는 Private Link로 격리돼 있어 연결이 시간 초과로 끊겼고, IAM 정책이 쓰기 API를 막아 열거는 되지만 변경은 되지 않았으며, CI 실행 정책이 악성 PR의 파이프라인 탈취를 막았습니다.

한 가지 더. 조사팀이 로그를 분석하려 하자 상용 모델의 안전 가드레일이 공격 코드 역분석을 거부해서, 내부에 오픈소스 모델(GLM-5.2)을 올려 분석했습니다. 공격도 방어도 AI가 한 셈입니다.

## 백엔드 개발자가 가져갈 것

이 사고에서 새로 배울 보안 원칙은 거의 없습니다. 이미 아는 것을 안 지켰을 때 대가가 얼마나 커지는지를 보여줄 뿐입니다. 에이전트가 17,600번을 시도하며 막히면 채널을 바꾸고 실패한 경로를 즉시 갈아치우는 속도 앞에서는, 평범한 약점 하나하나가 훨씬 비싸집니다. 정리하면 네 가지입니다.

- **에이전트를 특권 내부자로 취급합니다.** 사람 계정에 적용하는 최소 권한·짧은 수명·행위 감사를 자동화 신원에도 똑같이 겁니다.
- **메타데이터와 파드 권한을 닫습니다.** 파드 레벨 IMDS 접근 차단, 특권/hostPath 파드 어드미션 거부는 이번에 뚫린 바로 그 경로입니다.
- **자격증명 범위를 쪼갭니다.** "하나로 여러 클러스터 관리자"는 사고를 국소가 아니라 전면으로 키웁니다. 클러스터별로 격리하고 워크로드 아이덴티티로 옮깁니다.
- **평가·샌드박스를 운영보다 더 세게 격리합니다.** 안전장치를 낮춘 실험 환경일수록 경계를 강하게 그어야 합니다. 이번 사고의 시작점이 바로 그 반대였습니다.

버틴 방어들의 공통점이 답을 말해 줍니다. 화려한 새 도구가 아니라, Private Link·IAM 거부·CI 정책처럼 **좁게 그은 경계**가 기계 속도의 공격을 실제로 멈춰 세웠습니다.
