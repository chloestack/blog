## 개요

### 문제 배경: 비결정적 시스템의 품질 보장

**LLM 에이전트 Evals**는 단순 챗봇 응답 평가를 넘어, 도구 호출·메모리 참조·외부 API 연동이 복합적으로 얽힌 에이전트 시스템 전체를 체계적으로 검증하는 방법론입니다. 실제 프로젝트에서 에이전트를 배포한 팀들이 공통적으로 마주치는 어려움은 "모델을 업그레이드했더니 예상치 못한 곳에서 동작이 달라졌다"는 것입니다. 이 글을 읽고 나면 트레이스 기반 평가 체계를 어떻게 설계하고, 자동화 파이프라인과 연결하는지 이해할 수 있습니다.

에이전트 시스템이 단순 API 호출과 다른 점은 **추론 경로의 다양성**에 있습니다. 같은 사용자 질의에도 에이전트는 서로 다른 도구를 선택하거나, 다른 순서로 정보를 수집하거나, 다른 맥락에서 최종 응답을 생성할 수 있습니다. 이 비결정성이 에이전트를 강력하게 만드는 동시에, 품질 보장을 어렵게 만드는 근본 원인입니다. 단순히 최종 출력만 비교하는 테스트로는 "왜 올바른 결과가 나왔는가", "다음 번에도 올바른 결과가 나올 것인가"를 판단하기 어렵습니다.

### 기존 방식의 한계

전통적인 소프트웨어 품질 보증 방법론은 결정론적 입출력을 전제로 합니다. LLM 기반 시스템에 규칙 기반 테스트를 적용하면 세 가지 문제가 드러납니다. 첫째, **취성(brittleness)**: 모델 버전 변경만으로도 의미는 동일하지만 표현이 달라진 출력이 테스트를 실패시킵니다. 둘째, **불완전한 커버리지**: 에이전트가 어떤 도구를 왜 호출했는지, 중간 추론 단계가 올바른지를 검증하지 못합니다. 셋째, **확장 불가능한 수동 검토**: 에이전트 기능이 늘어날수록 사람이 직접 확인해야 하는 케이스가 기하급수적으로 증가합니다.

**트레이스 기반 평가**는 에이전트가 실행하는 모든 단계를 구조화된 데이터로 기록하여, 이 세 가지 문제를 동시에 해결하는 접근법입니다. 최종 출력이 아니라 추론 경로 자체를 평가 대상으로 삼기 때문에, 표현이 달라져도 의미가 동등하면 통과하고, 경로가 달라지면 상세하게 분석할 수 있습니다.

## LLM 에이전트 Evals의 핵심 개념

### 평가 계층 구조와 피드백 루프

LLM 에이전트 Evals는 **단위·통합·시스템**이라는 세 계층 구조로 이해하는 것이 가장 효과적입니다. **단위 평가(Unit Eval)**는 특정 프롬프트 템플릿 하나, 도구 호출 로직 하나를 격리하여 검증합니다. 주어진 맥락에서 올바른 도구를 선택하는지, 파라미터를 정확하게 추출하는지, 응답 형식이 스키마를 준수하는지를 확인합니다. **통합 평가(Integration Eval)**는 두 개 이상의 컴포넌트가 연결되는 시나리오를 다룹니다. 검색-증강 생성(RAG)에서 검색 결과가 실제 답변에 올바르게 활용되는지, 도구 체인이 순서대로 실행되는지 등이 대상입니다. **시스템 평가(System Eval)**는 실제 사용자 시나리오를 그대로 재현하여 전체 품질을 측정합니다.

이 계층을 구분하는 핵심 이유는 **피드백 루프의 속도와 비용**이 본질적으로 다르기 때문입니다. 단위 평가는 LLM 호출 없이 목(mock)으로 실행하면 수백 케이스를 초 단위에 처리할 수 있습니다. 반면 시스템 평가는 실제 LLM을 호출하므로 케이스당 수 초에서 수십 초가 소요됩니다. CI/CD 파이프라인에 단위 평가와 통합 평가를 먼저 통과시킨 뒤, 시스템 평가는 배포 전 최종 승인 게이트로 사용하는 패턴이 효율적입니다. 세 계층 모두를 갖추지 않으면 하나가 나머지를 대체할 수 없습니다. 단위 평가만으로는 컴포넌트 간 상호작용 문제를 포착하지 못하고, 시스템 평가만으로는 어느 단계에서 문제가 발생했는지 격리하기 어렵습니다.

### 트레이스란 무엇인가

**트레이스(Trace)**는 에이전트가 하나의 요청을 처리하면서 수행한 모든 동작의 구조화된 기록입니다. 각 단계를 **스팬(Span)**이라는 단위로 캡처하며, 스팬에는 타임스탬프, 입력, 출력, 오류 정보, 도구 이름, 토큰 사용량 등이 포함됩니다. 분산 시스템의 OpenTelemetry 트레이싱과 개념적으로 동일하며, LLM 생태계에서는 **LangSmith**, **Arize Phoenix**, **Weights & Biases Weave** 같은 도구들이 이 역할을 담당합니다.

트레이스가 단순 로그와 근본적으로 다른 점은 **계층적 구조**를 가진다는 것입니다. 에이전트 실행 전체를 루트 스팬으로, 개별 LLM 호출·도구 실행·검색 쿼리를 자식 스팬으로 구성하면, 어느 단계에서 얼마나 시간이 걸렸는지, 어느 스팬에서 오류가 발생했는지를 계층적으로 분석할 수 있습니다. 이 구조화된 데이터가 자동화된 평가의 원천이 됩니다.

### 평가자 유형과 조합 전략

Evals에서 **평가자(Evaluator)**는 트레이스 또는 최종 출력을 받아 점수나 레이블을 반환하는 함수입니다. 평가자 유형을 잘못 선택하면 비용 낭비 또는 신뢰성 손실로 이어지므로, 각 유형의 특성을 명확히 이해해야 합니다. **규칙 기반 평가자**는 JSON 스키마 준수 여부, 특정 필드 존재 여부, 도구 호출 횟수 같은 구조적 속성을 빠르고 확실하게 검증합니다. **모델 기반 평가자(LLM-as-Judge)**는 언어 모델을 사용하여 응답의 사실성·관련성·유해성 같은 주관적 품질을 평가합니다. 두 유형을 조합하는 것이 현실적인 접근입니다. 규칙 기반으로 빠르게 명백한 실패를 걸러내고, 모델 기반으로 미묘한 품질 차이를 평가하면 비용과 정확도를 동시에 최적화할 수 있습니다.

| 평가자 유형 | 속도 | 비용 | 강점 | 언제 쓰나 |
|---|---|---|---|---|
| 규칙 기반 | 매우 빠름 | 낮음 | 구조 검증에 신뢰도 높음 | 스키마, 형식, 필드 존재 여부 |
| LLM-as-Judge | 보통 | 중간~높음 | 의미·품질 평가에 적합 | 관련성, 사실성, 유해성 |
| 인간 평가 | 느림 | 높음 | 가장 신뢰 가능한 기준 | 기준선 설정, 판단 모호한 케이스 |

## 트레이스 기반 평가 설계

### 트레이스 수집 전략

트레이스를 수집하는 방법은 에이전트 프레임워크에 따라 다르지만, 공통된 원칙은 **계측(instrumentation)을 비즈니스 로직과 분리**하는 것입니다. 에이전트 코드 곳곳에 로깅을 직접 삽입하면 가독성이 떨어지고, 수집 전략이 바뀔 때마다 비즈니스 로직을 수정해야 합니다. 데코레이터나 컨텍스트 매니저 패턴을 사용하면 수집 로직을 투명하게 주입할 수 있습니다.

**OpenTelemetry** 표준을 따르는 계측 방식이 점점 중요해지고 있습니다. 특정 관측 가능성(Observability) 도구에 종속되지 않고, 수집된 트레이스를 여러 백엔드로 라우팅할 수 있기 때문입니다. LangChain의 경우 `LANGCHAIN_TRACING_V2=true` 환경 변수만 설정하면 LangSmith로 자동 트레이스가 전송됩니다. 커스텀 에이전트라면 `opentelemetry-sdk`를 직접 계측하는 것이 가장 유연한 접근입니다.


계측 레이어가 에이전트 코드와 수집 백엔드 사이를 중재하여, 백엔드를 교체해도 에이전트 코드는 전혀 수정할 필요가 없습니다.

아래는 Python에서 커스텀 에이전트에 OpenTelemetry 기반 트레이스를 삽입하는 예시입니다. 에이전트 클래스의 각 메서드가 개별 스팬으로 기록되도록 데코레이터를 활용합니다.

```python
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from functools import wraps

# 트레이서 초기화
provider = TracerProvider()
provider.add_span_processor(
    BatchSpanProcessor(OTLPSpanExporter(endpoint="http://localhost:4317"))
)
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("agent.eval")

def traced(span_name: str):
    """에이전트 메서드에 투명하게 트레이스를 삽입하는 데코레이터."""
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            with tracer.start_as_current_span(span_name) as span:
                if kwargs.get("query"):
                    span.set_attribute("input.query", str(kwargs["query"]))
                try:
                    result = func(*args, **kwargs)
                    span.set_attribute("output.result", str(result)[:500])
                    return result
                except Exception as e:
                    span.record_exception(e)  # 오류 자동 캡처
                    raise
        return wrapper
    return decorator

class ResearchAgent:
    @traced("agent.search")
    def search(self, query: str) -> list[dict]:
        return search_tool(query)  # 결과: [{"title": "...", "content": "..."}]

    @traced("agent.synthesize")
    def synthesize(self, context: list[dict], query: str) -> str:
        return llm.invoke(f"Context: {context}\nQuestion: {query}")
        # 결과: 생성된 응답 문자열, 스팬에 최대 500자까지 기록됨
```

데코레이터 방식의 핵심 장점은 비즈니스 로직을 전혀 수정하지 않고도 모든 메서드 호출에 트레이스를 주입할 수 있다는 점입니다. `span.set_attribute`로 기록한 입출력 데이터는 이후 자동화 평가자가 읽는 원천 데이터가 됩니다.

### 스팬 설계 원칙

좋은 트레이스는 이후 평가 자동화의 품질을 결정합니다. 스팬 설계에서 지켜야 할 핵심 원칙은 세 가지입니다. 첫째, **의미 있는 경계 설정**: 스팬은 의미론적으로 독립된 작업 단위와 일치해야 합니다. 단순히 "LLM 호출"보다 "사용자 의도 분류"처럼 비즈니스 맥락이 드러나는 이름이 평가에 훨씬 유용합니다. 둘째, **충분한 컨텍스트 포함**: 평가자가 스팬만 보고도 해당 단계가 올바른지 판단할 수 있도록, 입력·출력·사용된 모델·토큰 수·실행 시간을 기록합니다. 셋째, **민감 정보 마스킹**: 사용자 PII나 비즈니스 기밀이 트레이스 저장소에 평문으로 저장되지 않도록 수집 단계에서 필터링 계층을 두어야 합니다.

스팬 설계에서 자주 발생하는 실수는 너무 세분화하거나 너무 뭉뚱그리는 것입니다. 토큰 단위로 스팬을 만들면 노이즈가 심해지고, 에이전트 실행 전체를 스팬 하나로 묶으면 어느 단계에서 문제가 발생했는지 알 수 없습니다. 경험적으로 "하나의 외부 시스템 호출 또는 하나의 LLM 추론 단계"를 스팬의 단위로 삼는 것이 적절한 균형입니다.

> 스팬은 "나중에 이 단계만 잘라내어 평가할 수 있는가"를 기준으로 경계를 정하면 대부분 올바른 답이 나옵니다.

## 자동화 테스트 파이프라인 구축

### 평가 데이터셋 관리

자동화된 Evals의 근본은 **평가 데이터셋(Eval Dataset)**입니다. 데이터셋은 입력 케이스, 기대 동작, 그리고 가능하다면 기준 정답으로 구성됩니다. 데이터셋 품질이 곧 평가 신뢰도를 결정하므로, 구성 방법에 신중을 기해야 합니다. 세 가지 소스로 데이터셋을 구성하는 것이 효과적입니다. 첫째, **골든 케이스(golden cases)**: 도메인 전문가가 검토한 대표적 시나리오로, 회귀 테스트의 핵심입니다. 에이전트가 반드시 올바르게 처리해야 하는 케이스들을 수동으로 큐레이션합니다. 둘째, **프로덕션 샘플링**: 실제 운영 중 수집된 트레이스 중 대표성 있는 케이스를 선별합니다. 현실의 사용 패턴을 반영하므로 골든 케이스가 놓치는 다양성을 보완합니다. 셋째, **엣지 케이스 생성**: LLM을 활용하여 경계 조건이나 실패하기 쉬운 시나리오를 자동으로 생성합니다. 특히 적대적 입력이나 불완전한 쿼리 처리를 검증하는 데 유용합니다.

데이터셋 버전 관리도 반드시 필요합니다. 에이전트 시스템이 발전하면서 평가 기준도 달라지므로, 데이터셋 변경 이력을 코드와 함께 git으로 추적하거나 전용 데이터셋 레지스트리를 사용해야 합니다. 평가 기준과 데이터셋이 동기화되지 않으면 과거 모델과의 공정한 비교가 불가능해지고, 점수 개선이 진짜 품질 향상인지 평가 기준 완화인지 구분하기 어려워집니다.

### CI/CD 통합

에이전트 코드 변경이 기존 동작을 손상시키지 않도록 Evals를 CI/CD 파이프라인에 통합하는 것이 운영 자동화의 핵심입니다. PR이 열릴 때마다 단위·통합 평가가 자동으로 실행되고, 점수가 기준치 아래로 떨어지면 병합을 차단하는 구조가 이상적입니다. **동기 패턴**은 CI 단계에서 평가를 실행하고 결과를 기다립니다. LLM 호출이 포함된 평가는 시간이 오래 걸리므로, 단위 평가만 동기로 처리하고 통합·시스템 평가는 비동기로 처리하는 것이 현실적입니다. **비동기 패턴**은 배포 후 일정 시간이 지난 시점의 프로덕션 트레이스를 평가하여 회귀 여부를 감지합니다.

아래는 평가 파이프라인의 핵심 로직 예시입니다. 평가 점수를 CI 종료 코드로 전파하여 자동으로 병합을 차단합니다.

```python
# eval_pipeline.py — CI에서 실행되는 평가 파이프라인
import json
from pathlib import Path
from evaluators import ToolSelectionEvaluator, ResponseQualityEvaluator
from agent import ResearchAgent

def run_eval(dataset_path: str, threshold: float = 0.8) -> dict:
    dataset = json.loads(Path(dataset_path).read_text())
    agent = ResearchAgent()
    evaluators = [
        ToolSelectionEvaluator(),      # 도구 선택 정확도 평가
        ResponseQualityEvaluator(),    # LLM-as-Judge 기반 품질 평가
    ]

    results = []
    for case in dataset["cases"]:
        trace = agent.run_with_trace(case["input"])  # 트레이스 포함 실행
        scores = {
            ev.__class__.__name__: ev.evaluate(trace, case.get("expected"))
            for ev in evaluators
        }
        results.append({"case_id": case["id"], "scores": scores})

    avg_scores = {
        key: sum(r["scores"][key] for r in results) / len(results)
        for key in results[0]["scores"]
    }
    # 결과: {"ToolSelectionEvaluator": 0.91, "ResponseQualityEvaluator": 0.84}

    passed = all(v >= threshold for v in avg_scores.values())
    return {"passed": passed, "avg_scores": avg_scores, "details": results}

if __name__ == "__main__":
    result = run_eval("datasets/golden_cases.json")
    print(json.dumps(result, indent=2))
    exit(0 if result["passed"] else 1)  # CI 종료 코드로 품질 게이트 작동
```

`exit(0 if result["passed"] else 1)` 패턴이 핵심인 이유는 평가 실패를 CI 파이프라인의 실제 오류로 전파하여 자동으로 병합을 차단하기 때문입니다. 단순히 로그를 출력하는 것만으로는 자동화된 품질 게이트가 작동하지 않습니다.

### 회귀 감지와 알림

자동화 파이프라인의 최종 목표는 **품질 회귀를 배포 전에 감지**하는 것입니다. 이를 위해 기준선(baseline) 점수를 별도로 저장하고, 새로운 실행 결과와 통계적으로 비교하는 체계가 필요합니다. 단순히 임계값보다 낮은지만 비교하면, 임계값 바로 위에서 미세하게 하락하는 추세를 놓치는 경향이 있습니다. **통계적 유의성 검정(t-test, Mann-Whitney U)** 또는 **이동 평균 기반 이상 감지**를 적용하면 작은 회귀도 신뢰성 있게 탐지할 수 있습니다. 회귀가 확인되면 Slack이나 PagerDuty를 통해 즉시 알림을 발송하고, 변경사항 병합을 차단하여 품질 문제가 프로덕션으로 흘러가지 않도록 합니다.

## 평가 지표 설계와 트레이드오프

### 도구 호출 정확도

에이전트 평가에서 가장 직관적인 지표 중 하나는 **도구 호출 정확도(Tool Call Accuracy)**입니다. 주어진 사용자 의도에 대해 에이전트가 올바른 도구를 선택했는지, 도구 파라미터를 정확하게 추출했는지를 측정합니다. 이 지표가 중요한 이유는 도구 선택 오류가 연쇄적 실패를 유발하기 때문입니다. 검색 도구 대신 계산 도구를 호출하면 이후 모든 추론이 잘못된 전제 위에 쌓이게 됩니다.

정확도를 측정하는 방법에는 두 가지 접근이 있습니다. **Exact Match**는 기대 도구 이름과 파라미터가 완전히 일치하는지 확인합니다. 빠르고 명확하지만, 파라미터 표현이 약간 달라도 오류로 처리하는 취성을 가집니다. **Semantic Match**는 LLM 평가자를 사용하여 "의미적으로 동등한 도구 호출인가"를 판단합니다. 더 유연하지만 비용이 높고, 평가자 자체의 일관성을 별도로 검증해야 합니다. 두 방식 중 하나를 선택하는 것이 아니라, Exact Match로 빠르게 명확한 오류를 탐지하고 경계 케이스에만 Semantic Match를 적용하는 조합이 권장됩니다.

### 최종 응답 품질 지표

최종 응답을 평가하는 지표는 에이전트의 목적에 따라 달라집니다. **RAGAS**는 RAG 시스템에 특화된 평가 프레임워크로, 충실도(Faithfulness), 답변 관련성(Answer Relevancy), 컨텍스트 정밀도(Context Precision), 컨텍스트 재현율(Context Recall)을 자동으로 측정합니다. 이 네 지표는 서로 보완적이면서도 독립적으로 의미를 가집니다. 충실도가 낮으면 에이전트가 검색 결과를 무시하고 환각을 생성하는 것이고, 컨텍스트 재현율이 낮으면 관련 문서 자체를 검색하지 못한 것입니다. 네 지표를 동시에 추적해야 어디서 품질을 개선해야 하는지 방향이 보입니다.

| 지표 | 측정 대상 | 낮을 때 의미 | 주의점 |
|---|---|---|---|
| 충실도 (Faithfulness) | 응답이 컨텍스트에 근거하는가 | 환각 발생 가능성 높음 | 긴 응답에서 일부 오류만 있어도 낮게 평가됨 |
| 답변 관련성 | 질문에 직접 답하는가 | 주제에서 벗어난 응답 | 관련은 있지만 불완전한 경우 구분 어려움 |
| 컨텍스트 정밀도 | 검색된 문서가 유용한가 | 노이즈 문서 포함 | 재순위화(reranking)로 개선 가능 |
| 컨텍스트 재현율 | 필요한 정보를 검색했는가 | 정보 누락 | 청크 크기·임베딩 모델에 민감 |

### LLM-as-Judge 설계

**LLM-as-Judge**는 다른 LLM의 출력을 평가하는 LLM을 사용하는 패턴입니다. 인간 평가자와의 상관관계가 높다는 것이 여러 연구에서 확인되었으며, 확장 가능한 품질 평가의 현실적인 대안으로 자리잡고 있습니다. 그러나 설계 시 반드시 고려해야 할 편향이 있습니다. 첫째, **위치 편향(position bias)**: 평가자 LLM이 응답 A와 B를 비교할 때 먼저 제시된 응답을 선호하는 경향이 있습니다. 두 응답의 순서를 바꿔 두 번 실행하고 결과를 평균하면 이 편향을 크게 완화할 수 있습니다. 둘째, **자기 선호(self-enhancement bias)**: 동일한 모델 계열이 평가자와 피평가자로 사용될 때 자신의 스타일을 선호하는 경향이 있습니다. 강력하고 다양한 모델을 평가자로 사용하고, 평가자 일치율(Inter-annotator agreement)을 주기적으로 측정해야 합니다.

## 운영 환경 적용 시 고려사항

### 흔한 실수와 함정

Evals를 실제 프로젝트에 도입할 때 가장 자주 마주치는 실수는 **평가 데이터 누출(data leakage)**입니다. 평가 데이터셋이 파인튜닝이나 프롬프트 최적화에 사용되면, 에이전트가 평가 케이스에 과적합하여 실제 성능을 과대평가하게 됩니다. 이를 방지하려면 평가 데이터셋을 개발팀이 직접 접근하지 못하도록 별도 저장소에 격리하거나, 최소한 평가에 사용된 케이스와 개발에 사용된 케이스를 엄격히 구분해야 합니다.

두 번째 함정은 **지표 최적화 함정(Goodhart's Law)**입니다. 특정 평가 지표를 최적화 목표로 삼으면, 그 지표는 더 이상 실제 품질을 반영하지 못하게 됩니다. 충실도 점수를 높이기 위해 에이전트가 컨텍스트를 그대로 복사하는 방향으로 학습되면, 실제 사용자에게는 유용하지 않은 응답을 생성하게 됩니다. 여러 지표를 복합적으로 추적하고, 지표 변화가 실제 사용자 만족도와 상관관계를 유지하는지 정기적으로 검증해야 합니다. 세 번째로 흔한 실수는 **평가 비용 미고려**입니다. LLM-as-Judge 평가자를 모든 케이스에 무제한 적용하면 평가 비용이 에이전트 서비스 운영 비용을 초과하는 상황이 발생할 수 있습니다. 비용 효율적인 접근은 규칙 기반 평가자로 빠르게 필터링하고, LLM-as-Judge는 불확실한 케이스나 핵심 회귀 감지에만 사용하는 것입니다.

규칙 기반으로 명확한 실패를 먼저 걸러내면 LLM-as-Judge 호출 횟수를 크게 줄여 평가 비용을 통제할 수 있습니다.

### 모니터링과 디버깅

프로덕션 에이전트의 품질을 지속적으로 추적하려면 **실시간 평가 모니터링** 체계가 필요합니다. 모든 트레이스를 실시간으로 평가하는 것은 비용과 지연 측면에서 비현실적이므로, 통계적 샘플링을 적용합니다. 무작위 샘플링보다 **계층적 샘플링(stratified sampling)**이 효과적입니다. 오류가 발생한 케이스, 응답 지연이 긴 케이스, 신규 사용자 유형에서 발생한 케이스에 더 높은 가중치를 부여하여 샘플링하면, 같은 평가 비용으로 더 많은 품질 정보를 얻을 수 있습니다.

디버깅 시에는 트레이스의 계층적 구조가 핵심 도구가 됩니다. 최종 응답 품질이 낮을 때 루트 스팬에서 시작하여 자식 스팬을 순서대로 확인하면, 도구 호출 단계에서 잘못된 정보가 들어왔는지, LLM 추론 단계에서 오류가 발생했는지를 빠르게 격리할 수 있습니다. **트레이스 비교(trace diffing)** 기능을 갖춘 LangSmith나 Arize Phoenix는 두 트레이스를 나란히 놓고 어느 스팬에서 차이가 발생했는지를 시각적으로 보여주어, 회귀의 원인을 신속하게 좁히는 데 도움을 줍니다.

### 확장과 마이그레이션

에이전트 시스템이 성장하면 Evals 인프라도 함께 확장해야 합니다. 처음에는 단일 파이프라인으로 충분하지만, 에이전트 수가 늘고 데이터셋이 커지면 **병렬 평가 실행**이 필요합니다. 케이스를 배치로 나누어 여러 워커에서 동시에 평가하면 전체 실행 시간을 선형적으로 줄일 수 있습니다. 또한 **평가 캐싱**도 중요합니다. 동일한 입력에 대해 LLM-as-Judge를 반복 호출하지 않도록 결과를 캐싱하면, 특히 회귀 테스트에서 비용을 크게 절감할 수 있습니다.

모델을 마이그레이션할 때 — 예를 들어 GPT-4 Turbo에서 Claude 3.5 Sonnet으로 전환할 때 — 기존 Evals 데이터셋이 비교 기준선을 제공합니다. 새 모델을 기존 데이터셋으로 평가하여 회귀가 없는지 확인한 뒤 점진적으로 트래픽을 전환하는 **A/B 배포 패턴**이 안전합니다. 이때 트레이스에 모델 버전을 메타데이터로 포함시켜야, 나중에 모델별 성능 추이를 분석하고 롤백 결정에 데이터를 활용할 수 있습니다.

## 맺음말

### 핵심 요약

LLM 에이전트 Evals는 단순한 테스트 도구가 아니라 에이전트 시스템의 품질을 지속적으로 측정하고 개선하는 엔지니어링 기반 시스템입니다. 트레이스 기반 평가는 최종 출력만 검증하는 방식을 넘어, 에이전트가 목표에 도달하는 과정 자체를 투명하게 만듭니다. 단위·통합·시스템이라는 계층 구조로 평가를 설계하고 CI/CD에 통합하면, 모델 업그레이드나 프롬프트 변경이 기존 동작에 미치는 영향을 배포 전에 감지할 수 있습니다. 규칙 기반 평가자와 LLM-as-Judge를 조합하여 비용과 정확도를 균형 있게 유지하고, 프로덕션 트레이스를 지속적으로 샘플링하여 실제 사용 패턴의 변화를 반영하는 것이 장기적으로 신뢰성 있는 에이전트를 운영하는 방법입니다.

### 적용 판단 기준

에이전트가 단일 LLM 호출 수준이라면 단위 평가와 기본적인 출력 검증만으로 충분할 수 있습니다. 반면 다음 조건 중 하나 이상에 해당한다면 체계적인 트레이스 기반 Evals 투자가 타당합니다. **다수의 도구를 조합하거나 멀티스텝 추론을 수행하는 경우**, 도구 호출 정확도와 연쇄 실패 감지가 핵심이 됩니다. **모델 버전 업그레이드를 반복하는 경우**, 기준선이 없으면 어떤 변경이 품질에 영향을 미쳤는지 추적할 수 없습니다. **프로덕션 트래픽이 높아 수동 품질 검토가 불가능한 경우**, 자동화 없이는 품질 보증의 공백이 생깁니다. 처음 도입할 때는 골든 케이스 20~50개와 규칙 기반 평가자부터 시작하고, 시스템이 안정화되면 LLM-as-Judge와 자동 데이터셋 확장을 단계적으로 추가하는 접근이 현실적입니다.
