## 개요

Cursor Rules는 AI 코딩 에이전트인 Cursor가 코드를 생성하거나 편집할 때 자동으로 참고하는 프로젝트 전용 지침 파일입니다. 아무런 컨텍스트 없이 동작하는 AI는 범용적인 패턴만 생성하지만, 잘 설계된 Rules가 있으면 팀의 아키텍처 결정, 도메인 지식, 코딩 컨벤션까지 반영한 코드를 내놓습니다. 이 글은 Cursor Rules를 단순한 스타일 파일이 아닌 AI 에이전트와 프로젝트 사이의 지속적 인터페이스로 설계하는 방법을 다룹니다.

### 문제 배경: AI 에이전트의 컨텍스트 공백

AI 코딩 도구가 실제 프로젝트에 투입될 때 가장 먼저 부딪히는 문제는 컨텍스트 단절입니다. GPT-4나 Claude 같은 대형 언어 모델은 수억 건의 코드를 학습했지만, 당신의 팀이 `UserRepository`와 `UserService`를 어떻게 구분하는지, API 응답에 어떤 에러 코드 체계를 쓰는지, 특정 레거시 모듈을 왜 건드리지 않기로 결정했는지는 전혀 모릅니다. 결국 AI가 생성한 코드는 컴파일은 되지만 팀 컨벤션에 맞지 않아 리뷰에서 걸리거나, 이미 내부 유틸리티가 있는데 외부 라이브러리를 새로 import하는 상황이 반복됩니다.

이 문제를 해결하는 전통적인 방법은 채팅창에 긴 배경 설명을 붙여넣는 것이었습니다. "우리 프로젝트는 Spring Boot 3을 사용하고, Repository는 JPA를 사용하며..." 하지만 이 방식은 세 가지 치명적인 단점이 있습니다. 첫째, 매 대화를 시작할 때마다 같은 내용을 반복해야 합니다. 둘째, 팀원마다 다른 설명을 붙이면 AI의 행동이 일관되지 않습니다. 셋째, 설명이 길어질수록 컨텍스트 창을 잠식해 실제 작업에 쓸 수 있는 토큰이 줄어듭니다.

### 기존 방식의 한계: 프롬프트 복붙의 비효율

프로젝트 컨텍스트를 개인 설정에만 저장하는 방식도 한계가 명확합니다. Cursor의 사용자 설정(User Rules)은 모든 프로젝트에 공통으로 적용되므로, 특정 프로젝트의 기술 스택이나 팀 규칙을 담기에는 너무 넓습니다. 반대로 코드 주석이나 README에 컨벤션을 적어두는 방식은 AI가 자동으로 읽지 않기 때문에 수동으로 대화에 포함시켜야 하는 번거로움이 남습니다. 결국 AI가 생성하는 코드의 품질은 개발자가 그날 얼마나 설명을 성실하게 붙였느냐에 달려 있게 됩니다.

## Cursor Rules의 동작 원리

Cursor Rules는 Cursor 에디터가 AI 요청을 처리할 때 시스템 프롬프트에 자동으로 삽입하는 텍스트 파일입니다. 개발자가 별도로 언급하지 않아도, 현재 열려 있는 파일의 경로와 규칙 파일의 적용 범위를 매칭해 관련 규칙을 자동으로 포함시킵니다. 이 메커니즘을 정확히 이해하면 어느 규칙이 언제 활성화되는지 예측할 수 있고, 불필요한 규칙이 포함되어 토큰을 낭비하는 상황을 방지할 수 있습니다.

### 규칙 파일의 적용 메커니즘

Cursor 0.43 버전부터 규칙 파일은 `.cursor/rules/` 디렉토리 아래 `.mdc` 확장자 파일로 저장됩니다. 각 파일은 YAML front matter로 적용 범위를 선언하고, 본문에 지침을 담습니다. 적용 방식은 네 가지입니다. **Always**는 모든 AI 상호작용에 항상 포함됩니다. **Auto Attached**는 `globs` 패턴에 매칭되는 파일이 열려 있을 때 자동으로 포함됩니다. **Agent Requested**는 AI가 규칙 파일의 설명을 읽고 스스로 필요하다고 판단할 때 포함합니다. **Manual**은 개발자가 `@rulename`으로 명시적으로 호출할 때만 포함됩니다.

이 네 가지 방식은 각각 다른 규칙 유형에 적합합니다. 절대 어겨서는 안 되는 보안 원칙이나 전체 아키텍처 결정은 Always로, 특정 기술 스택에 맞는 세부 패턴은 Auto Attached로, 드물게 필요한 고급 절차(예: 마이그레이션 작성법)는 Agent Requested나 Manual로 구성하면 시스템 프롬프트 길이를 효율적으로 관리할 수 있습니다.

규칙이 시스템 프롬프트에 포함되는 네 가지 경로는 각각 다른 상황에서 활성화됩니다.

### 규칙의 우선순위와 병합 방식

여러 규칙 파일이 동시에 적용될 때 Cursor는 이를 하나의 시스템 프롬프트로 병합합니다. glob 패턴이 더 구체적인 규칙일수록 좁은 범위의 컨텍스트에 집중합니다. 예를 들어 `**/*.ts` 패턴의 TypeScript 일반 규칙과 `src/api/**/*.ts` 패턴의 API 레이어 규칙이 함께 적용될 때, API 파일을 열면 두 규칙이 모두 포함됩니다. 중요한 점은 동일한 주제에 대해 서로 충돌하는 지침이 있는 규칙 파일들이 동시에 적용되면 AI가 어느 쪽을 따를지 확신하기 어렵고, 결과의 일관성이 떨어진다는 것입니다. 따라서 규칙 파일 간 관심사 분리를 철저히 해야 하며, 범용 규칙에서 특정 레이어에 대한 세부 지침을 담지 않아야 합니다.

### 컨텍스트 전달의 핵심 원리

Cursor Rules가 효과적인 이유는 단순한 텍스트 삽입을 넘어, AI가 매 요청마다 최신 프로젝트 상태를 알고 작업을 시작하게 만들기 때문입니다. 사람에게 새 팀원을 온보딩할 때 아키텍처 문서를 읽히는 것처럼, Cursor Rules는 AI에게 매 대화마다 프로젝트 온보딩을 수행합니다. 사람은 한 번 읽으면 기억하지만, AI는 대화가 끝나면 상태가 초기화됩니다. Rules는 이 세션 간 컨텍스트 단절을 채우는 유일한 메커니즘입니다. 이 관점이 중요한 이유는, Rules를 단순한 설정 파일이 아닌 AI와의 장기적인 협업 계약서로 다루게 만들기 때문입니다.

## 효과적인 규칙 설계 전략

좋은 Cursor Rules는 "우리 팀은 탭 대신 스페이스를 쓴다" 수준의 스타일 지침을 넘어서야 합니다. AI가 코드를 작성할 때 실제로 영향을 받을 수 있는 결정, 즉 어떤 패턴을 쓸지, 어떤 라이브러리를 선택할지, 어떤 에러를 어떻게 처리할지에 대한 지침이 담겨 있을 때 Rules의 가치가 실현됩니다. 스타일은 린터와 포매터에 위임하고, Rules는 도구가 잡을 수 없는 아키텍처적 판단에 집중해야 합니다.

### 글로벌 규칙 vs. 레이어별 규칙

규칙의 적용 범위를 잘못 설정하면 두 가지 문제가 생깁니다. 너무 좁으면 관련 컨텍스트가 포함되지 않아 AI가 엉뚱한 코드를 생성하고, 너무 넓으면 불필요한 토큰을 소비해 실제 지침의 영향력이 희석됩니다. 글로벌 규칙(Always 타입)은 프로젝트 전반의 불변 원칙, 즉 "이 프로젝트의 언어는 Kotlin이고 Java 8 이하 문법은 쓰지 않는다", "모든 외부 서비스 호출은 Circuit Breaker를 통과해야 한다" 같은 규칙에 적합합니다.

반면 특정 모듈이나 레이어에 적용되는 세부 규칙은 Auto Attached 타입으로 glob 패턴을 좁게 잡아야 합니다. `src/domain/**`에는 도메인 모델 설계 원칙, `src/infrastructure/**`에는 외부 시스템 통합 패턴, `src/api/**`에는 HTTP 응답 형식 규칙을 따로 두면 각 레이어에서 정확한 지침이 제공됩니다. 이 구조는 단일 거대 규칙 파일과 비교할 때 유지보수 측면에서도 유리합니다. 기술 스택이 교체되거나 레이어 설계가 바뀔 때 관련 규칙만 업데이트하면 되기 때문입니다.

규칙을 레이어 단위로 분리하면 각 AI 요청에 필요한 지침만 정확하게 포함됩니다.

### 파일 범위와 관심사 분리

glob 패턴 설계는 생각보다 섬세한 작업입니다. `**/*.ts`처럼 전체 TypeScript 파일을 잡는 패턴은 넓지만 테스트 파일과 프로덕션 파일을 구분하지 않습니다. `**/*.spec.ts`와 `**/*.ts`를 같은 규칙에 묶으면, 테스트 파일에서는 전혀 필요 없는 프로덕션 코드 패턴 지침이 포함되어 AI가 테스트 코드를 작성할 때도 불필요한 제약을 받을 수 있습니다. 테스트 파일은 별도 규칙을 두어 Mock 전략, 테스트 픽스처 네이밍, assertion 스타일을 따로 지정하는 것이 효과적입니다.

관심사 분리의 또 다른 중요한 이유는 규칙 간 충돌 방지입니다. "API 레이어는 DTO를 반환한다"는 규칙과 "도메인 레이어는 Value Object를 사용한다"는 규칙이 같은 파일에 있으면, 레이어 경계에 위치한 파일에서 AI가 혼란을 겪을 수 있습니다. 각 규칙 파일이 단일 관심사만 다루도록 설계하면 이 문제를 원천 차단할 수 있습니다.

### 규칙 작성 문체와 구조

AI에게 지침을 전달할 때는 사람이 읽는 문서와 다른 원칙이 적용됩니다. AI는 모호한 표현보다 명확하고 구체적인 지시문에 더 일관되게 반응합니다. "가능하면 불변 객체를 선호한다" 대신 "모든 Value Object는 `final` 클래스로 선언하고 필드는 `private final`로 한다"처럼 행동을 직접 지시하는 문체가 효과적입니다. 이유가 필요한 경우 한 줄 주석처럼 간략하게 붙이면 AI가 규칙의 의도를 더 정확히 파악합니다.

규칙 파일은 짧고 열거형으로 작성하는 것이 좋습니다. 100줄이 넘는 규칙 파일은 토큰 비용도 높이고, AI가 모든 지침을 동등하게 반영하지 못할 가능성도 높아집니다. 규칙 파일 하나는 30~50줄 이내를 권장합니다.

| 항목 | 효과 낮은 예 | 효과 높은 예 |
|---|---|---|
| 구체성 | 좋은 코드를 작성할 것 | 메서드 길이는 30줄 이하로 유지할 것 |
| 행동 지향 | 에러 처리에 주의할 것 | checked exception은 use-case 레이어에서 unchecked로 변환할 것 |
| 단일 초점 | 아키텍처와 스타일 규칙 혼합 | 레이어별 책임만 기술 |
| 파일 길이 | 200줄 이상의 단일 파일 | 30~50줄, 레이어별 분리 |
| 금지 표현 | 이 클래스를 절대 수정하지 말 것 | 이 클래스 대신 XXXFacade를 사용할 것 |

## 실제 프로젝트에 적용하기

이론을 현업 프로젝트에 적용할 때 가장 많은 시행착오가 발생하는 세 가지 영역이 있습니다. 코드베이스의 구조적 컨텍스트를 전달하는 방법, 팀의 암묵적 컨벤션을 명문화하는 방법, 그리고 도메인 지식을 규칙에 인코딩하는 방법입니다. 각 영역은 서로 독립적으로 발전할 수 있어야 하므로, 규칙 파일을 주제 단위로 분리하는 것이 장기적으로 유리합니다.

### 코드베이스 컨텍스트 전달

AI가 가장 먼저 알아야 할 것은 코드베이스의 구조입니다. 단순히 "우리는 Hexagonal Architecture를 쓴다"고 적는 것보다, 실제 디렉토리 구조와 각 레이어의 책임을 구체적으로 기술하는 것이 훨씬 효과적입니다. 아래는 Spring Boot + Hexagonal Architecture 프로젝트의 글로벌 규칙 파일 예시입니다. `alwaysApply: true`로 설정해 모든 AI 요청에 포함됩니다.

```markdown
---
description: 프로젝트 전역 컨텍스트와 아키텍처 원칙
alwaysApply: true
---

# 프로젝트 개요
- 언어: Kotlin 1.9+, JVM 21
- 프레임워크: Spring Boot 3.3
- 아키텍처: Hexagonal Architecture (Ports & Adapters)

# 레이어 구조
- domain/: 순수 비즈니스 로직, 외부 의존성 없음
- application/: use-case 오케스트레이션, 포트 인터페이스 정의
- adapter/in/: HTTP, gRPC, 메시지 소비자 (인바운드 어댑터)
- adapter/out/: DB, 외부 API, 메시지 발행자 (아웃바운드 어댑터)

# 절대 원칙
- domain 레이어는 Spring, JPA 어노테이션을 import하지 않는다
- application 레이어는 adapter 패키지를 직접 참조하지 않는다
- 모든 외부 의존성은 포트 인터페이스를 통해서만 접근한다
- DTO는 adapter 레이어에만 존재한다. domain 객체를 응답으로 직접 반환하지 않는다
```

이 규칙이 없으면 AI는 Spring Data JPA를 모든 레이어에서 직접 사용하는 전형적인 코드를 생성합니다. 규칙이 있으면 포트 인터페이스를 통해 접근하는 올바른 패턴을 따릅니다. 이 차이는 단순한 스타일 문제가 아니라 아키텍처 결함 유발 여부의 차이입니다.


글로벌 규칙이 포함되면 AI는 아키텍처 원칙을 준수한 코드를 생성합니다.

### 팀 컨벤션 자동화

코딩 컨벤션은 팀마다 다르고, 일부는 외부에서 보면 이해하기 어려운 역사적 이유가 있습니다. "왜 이 프로젝트는 ResultWrapper 대신 Either 타입을 쓰나"처럼 맥락이 있는 결정을 규칙에 담으면 AI가 이유 없이 다른 패턴을 섞어 쓰는 것을 방지할 수 있습니다. 에러 처리 방식은 팀마다 가장 이견이 많은 영역이기도 합니다. 아래는 Arrow Kt의 Either를 사용하는 함수형 에러 처리 컨벤션 파일 예시입니다.

```markdown
---
description: 에러 처리 컨벤션 — Arrow Kt Either 사용
globs: ["src/application/**", "src/domain/**"]
---

# 에러 처리 원칙
- use-case 반환 타입은 Either<DomainError, T>를 사용한다 (Arrow Kt)
- 예외를 던지지 말 것. 실패는 Either.Left(DomainError)로 표현한다
- DomainError는 sealed class로 정의하고 모든 비즈니스 에러를 열거한다
- infrastructure 예외(DB, 네트워크)는 adapter에서 catch 후 DomainError로 변환한다

# DomainError 정의 위치
- domain/error/ 디렉토리에 비즈니스 도메인별로 파일 분리
- 예: UserError.kt, OrderError.kt
# 이 방식을 선택한 이유: 컴파일 타임에 에러 처리를 강제하고
# 예외 계층 복잡도를 제거하기 위함
```

이 규칙이 없으면 AI는 관용적인 Kotlin 예외 처리나 Java 스타일의 checked exception을 생성합니다. 규칙이 있으면 `Either.Left(UserError.NotFound)` 패턴을 사용합니다. 이유를 주석으로 담으면 AI가 단순히 패턴을 따르는 것을 넘어 관련 판단을 내릴 때도 일관된 방향을 유지합니다.

### 도메인 지식 인코딩

도메인 지식은 가장 인코딩하기 어렵지만, 제대로 담겼을 때 AI 코드 품질 차이가 가장 크게 나타납니다. 예를 들어 e-commerce 플랫폼에서 주문과 배송의 상태 전이 규칙, 특정 상품 카테고리에만 적용되는 할인 계산 로직, 외부 결제사와의 계약에서 비롯된 API 호출 제약이 이에 해당합니다. 이 지식이 없으면 AI는 일반적인 상태 머신 패턴을 생성하지만, 비즈니스 규칙에 위배되는 상태 전이를 허용하는 코드를 낼 수 있습니다.

## 트레이드오프와 대안 비교

Cursor Rules는 모든 상황에서 최선은 아닙니다. 도구 선택에는 항상 트레이드오프가 따르며, 다른 AI 코딩 에이전트나 컨텍스트 전달 방식과의 비교를 통해 언제 Rules가 효과적인지 파악해야 합니다. 특히 팀이 여러 AI 도구를 혼용하거나, 프로젝트 규모가 작은 경우에는 단순한 방식이 더 효율적일 수 있습니다.

### .cursorrules vs. `.cursor/rules/`

구버전 Cursor는 프로젝트 루트의 `.cursorrules` 단일 파일만 지원했습니다. 이 방식은 설정이 단순하지만 모든 규칙이 하나의 파일에 뭉쳐 있어, 파일이 길어질수록 유지보수가 어려워지고 특정 파일 유형에만 적용하는 세분화된 규칙을 표현할 수 없었습니다. `.cursor/rules/` 디렉토리 방식은 이 한계를 해결하지만 구조 설계에 더 많은 초기 투자가 필요합니다.

| 항목 | `.cursorrules` | `.cursor/rules/` |
|---|---|---|
| 지원 버전 | 레거시 (모든 버전) | Cursor 0.43+ |
| 구조 | 단일 파일 | 디렉토리 + 다중 파일 |
| 적용 범위 | 전체 프로젝트 항상 | 파일별 glob 매칭 가능 |
| 적용 타입 | Always만 | Always·Auto·Agent·Manual |
| 유지보수 | 파일 커질수록 어려움 | 레이어별 독립 유지 가능 |
| 권장 여부 | 소규모·단기 프로젝트 | 팀 프로젝트·장기 운영 |

### Cursor Rules vs. 다른 AI 코딩 도구

GitHub Copilot의 `.github/copilot-instructions.md`, Windsurf의 `.windsurfrules`, Aider의 `.aider.conf.yml`은 모두 유사한 목적을 가집니다. Copilot Instructions는 glob 패턴 기반 분기를 지원하지 않고 항상 전체에 적용됩니다. Windsurf는 Cascade 규칙으로 세부 분기를 지원하지만 Cursor보다 생태계가 작습니다. 이 파일들이 각 도구에 종속되기 때문에, 팀이 여러 AI 도구를 혼용한다면 규칙 파일의 동기화 관리가 별도로 필요하고, 도구마다 다른 형식에 맞게 규칙을 번역해야 하는 비용이 발생합니다.

```diagram

```

도구마다 규칙 파일 형식이 다르므로, 팀이 사용하는 AI 도구에 맞는 형식을 선택해야 합니다.

### 규칙 복잡도와 AI 성능의 균형

규칙이 많을수록 항상 좋은 것은 아닙니다. 과도하게 상세한 규칙은 두 가지 부작용이 있습니다. 첫째, 시스템 프롬프트가 길어져 모델이 모든 지침에 균등하게 집중하지 못합니다. 최신 연구에 따르면 LLM은 컨텍스트 창의 중간 부분에 있는 정보를 상대적으로 덜 반영하는 경향이 있습니다. 이는 규칙 파일이 매우 길면 중간 부분의 지침이 사실상 무시될 수 있다는 의미입니다. 둘째, 규칙이 너무 세부적이면 코드 변경에도 규칙 수정이 연쇄적으로 필요해 유지보수 비용이 증가합니다.

> 균형점은 "AI가 없으면 잘못된 결정을 내릴 가능성이 높은 것"에 집중하는 것입니다. 린터나 포매터로 강제할 수 있는 것은 Rules에 넣지 않아야 합니다.

## 운영 환경에서의 고려사항

Cursor Rules를 처음 도입할 때는 개인 설정 수준으로 시작하는 경우가 많습니다. 그러나 팀 전체가 일관된 AI 경험을 원한다면 Rules를 코드베이스의 일부로 관리해야 합니다. 이 전환 과정에서 흔히 발생하는 문제들과 장기 운영 전략을 살펴봅니다.

### 흔한 실수와 함정

가장 흔한 실수는 규칙을 한 번 작성하고 업데이트하지 않는 것입니다. 프로젝트는 계속 진화하는데 Rules가 6개월 전의 구조를 반영하면, AI는 이미 제거된 패턴이나 존재하지 않는 클래스를 참고해 잘못된 코드를 생성합니다. 규칙 파일도 코드처럼 리팩터링이 필요하며, 기술 스택이 변경되면 관련 규칙도 함께 수정해야 합니다.

두 번째 함정은 규칙을 통해 AI를 지나치게 제약하는 것입니다. "이 파일은 절대 수정하지 말 것", "이 라이브러리는 절대 사용하지 말 것"처럼 절대적인 금지 규칙이 많으면 AI의 유연성이 줄고, 정당한 상황에서도 규칙에 막혀 유용한 제안을 못 하게 됩니다. 금지보다는 "~을 대신 사용하라"처럼 대안을 제시하는 방식이 훨씬 효과적입니다.

```diagram
2026-10-11-dd544fa0-07
```

규칙은 금지보다 대안 제시 방식이 AI의 판단을 올바르게 유도하는 데 효과적입니다.

### 팀 협업과 규칙 버전 관리

`.cursor/rules/` 디렉토리는 반드시 Git으로 관리해야 합니다. 이 파일들은 코드베이스의 "AI 온보딩 문서"이기도 하고, 팀의 아키텍처 결정을 문서화하는 부산물이기도 합니다. 규칙 파일을 `.gitignore`에 추가하는 것은 팀의 AI 경험을 개인화해 일관성을 포기하는 것과 같습니다. 새로 합류한 팀원이 Rules를 읽으면 프로젝트의 기술적 결정과 그 이유를 빠르게 파악할 수 있다는 부수적 이점도 있습니다.

규칙 변경에는 코드 변경과 동일한 리뷰 프로세스를 적용하는 것이 좋습니다. 특히 글로벌 규칙(Always 타입)을 수정하는 것은 모든 AI 상호작용에 영향을 미치므로, 예상치 못한 부작용이 없는지 팀원과 확인해야 합니다. PR 단계에서 "이 규칙 변경이 다른 레이어의 AI 작업에 영향을 미치지 않는가"를 체크리스트에 포함시키면 의도치 않은 회귀를 방지할 수 있습니다.

### 규칙 효과 측정과 지속적 개선

Cursor Rules의 효과를 측정하는 직접적인 지표는 존재하지 않습니다. 그러나 간접 지표로 AI 코드 수용률(생성된 코드가 수정 없이 병합되는 비율), 코드 리뷰에서 반복되는 지적 사항의 감소, AI 생성 코드로 인한 아키텍처 위반 건수 등을 추적할 수 있습니다. 효과적인 규칙 개선 프로세스는 코드 리뷰에서 출발합니다. "AI가 이 패턴을 또 생성했다"는 리뷰 코멘트가 반복된다면 그것은 Rules에 해당 지침이 없다는 신호입니다.

```diagram
2026-10-11-dd544fa0-08
```

코드 리뷰 피드백을 Rules에 반영하는 순환 구조가 팀의 AI 코드 품질을 점진적으로 향상시킵니다.

리뷰에서 반복되는 지적을 모아 주기적으로 Rules에 추가하면, 시간이 지날수록 AI의 코드 품질이 향상되는 복리 효과가 나타납니다. 이 과정은 팀의 암묵지를 명시적 문서로 전환하는 부수적 효과도 낳습니다. 새 팀원이 온보딩할 때 Rules를 읽으면, 코드에서는 보이지 않던 "왜 이렇게 만들었는가"의 답을 얻을 수 있습니다.

## 맺음말

### 핵심 요약

Cursor Rules는 AI 코딩 에이전트에게 프로젝트 컨텍스트를 지속적으로 전달하는 핵심 메커니즘입니다. 글로벌 규칙과 레이어별 규칙을 분리하고, 각 규칙은 단일 관심사만 다루도록 설계해야 합니다. 규칙 파일은 코드처럼 Git으로 버전 관리하고, 코드 리뷰의 반복 피드백을 통해 지속적으로 개선하는 것이 장기 운영의 핵심입니다.

효과적인 규칙은 린터가 잡을 수 없는 아키텍처 결정과 도메인 지식에 집중합니다. 스타일은 코드 포매터에 맡기고, Rules는 AI가 혼자서는 알 수 없는 팀의 선택과 그 이유를 담는 데 집중해야 합니다. 규칙 파일 하나는 30~50줄 이내로 유지하고, 토큰 비용보다 지침의 명확성과 집중도를 우선하는 것이 좋습니다.

### 적용 판단 기준

Cursor Rules를 도입할 가치가 있는 상황은 명확합니다. 팀원이 AI 생성 코드에서 같은 문제를 반복적으로 지적한다면, AI가 이미 내부 유틸리티가 있는 기능을 외부 라이브러리로 구현한다면, 또는 아키텍처 레이어 경계를 AI가 자주 위반하는 코드를 생성한다면 Rules 설계가 필요한 시점입니다. 반대로 단기 개인 프로젝트나 탐색적 프로토타이핑에서는 간단한 `.cursorrules` 파일 하나로 시작하는 것이 오버엔지니어링 없이 충분한 효과를 냅니다.

팀 규모가 커질수록 Cursor Rules는 단순한 에디터 설정이 아닌, AI와 팀 사이의 협업 인터페이스가 됩니다. 코드베이스를 처음 접하는 팀원이 아키텍처 문서를 읽듯, AI는 매 대화에서 Rules를 통해 프로젝트의 판단 기준과 역사를 흡수합니다. 이 관점으로 Rules를 설계하면 단순한 프롬프트 최적화를 넘어 팀 전체의 기술 자산이 됩니다.
