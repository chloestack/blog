### 모니터링 지표

Qdrant는 Prometheus 형식의 메트릭을 `/metrics` 엔드포인트로 제공합니다. 운영 환경에서 반드시 추적해야 할 지표는 크게 세 범주입니다. **검색 성능** 관련으로는 `qdrant_requests_total`(요청 수), `qdrant_rest_response_duration_seconds`(레이턴시 분포), `qdrant_grpc_response_duration_seconds`(gRPC 레이턴시)를 봅니다. 레이턴시 p99가 SLA를 초과하기 시작하면 `hnsw_ef` 설정을 낮추거나 양자화를 도입하거나 샤드를 추가해 부하를 분산하는 방향을 검토합니다.

**인덱스 상태** 관련으로는 컬렉션별 세그먼트 수를 추적합니다. 세그먼트 수가 비정상적으로 많다면 최적화(optimization)가 충분히 실행되지 않는 신호입니다. Qdrant는 백그라운드에서 세그먼트를 병합하고 인덱스를 재빌드하는 최적화 프로세스를 실행하는데, 쓰기 처리량이 높으면 최적화가 따라가지 못하는 상황이 발생합니다. 이때는 `optimizer_config`의 `default_segment_number`를 늘리거나 최적화 병렬도를 조정합니다.

**자원 사용** 측면에서는 RAM 사용량이 가장 중요합니다. 벡터와 HNSW 그래프를 모두 메모리에 올리는 기본 설정에서 메모리 부족이 발생하면 mmap 스왑이 일어나 레이턴시가 급등합니다. 가용 RAM의 80% 이하로 사용량을 유지하는 것을 목표로 하되, 실제 운영 중에는 OS 페이지 캐시까지 고려한 메모리 계획이 필요합니다.

| 지표 | 정상 범위 | 주의 신호 | 대응 방안 |
|---|---|---|---|
| p99 레이턴시 | < 100ms | > 200ms | hnsw_ef 감소, 양자화 도입 |
| 세그먼트 수 | < 10개 | > 30개 | optimizer 설정 조정 |
| RAM 사용률 | < 80% | > 90% | 양자화, on_disk 전환 |
| indexed_vectors 비율 | > 95% | < 80% | 쓰기 속도 조절 |

### 확장 전략

Qdrant의 수평 확장은 샤드 추가와 노드 추가 두 가지 축으로 이루어집니다. 벡터 데이터가 증가해 단일 노드에서 RAM이 부족해지는 경우, 새 노드를 클러스터에 추가하고 기존 샤드의 일부를 이동하거나 새 샤드를 추가합니다. 샤드 이동은 온라인으로 이루어지며 서비스 중단 없이 진행됩니다. 단, 이동 중인 샤드는 I/O 부하가 높아지므로 트래픽이 낮은 시간대를 택하거나 이동 속도를 제한하는 설정을 활용합니다.

쿼리 처리량이 병목이라면 **읽기 전용 복제본**을 추가하는 것이 효과적입니다. Qdrant의 복제본은 모두 읽기/쓰기가 가능하지만, 클라이언트 로드밸런서에서 특정 복제본을 읽기 전용으로 지정하는 방식으로 읽기 트래픽을 분산할 수 있습니다.

## 운영 환경 적용 시 주의사항

### 흔한 실수와 함정

Qdrant를 처음 프로덕션에 적용할 때 가장 자주 겪는 문제는 **컬렉션 재생성 비용**을 과소평가하는 것입니다. 잘못된 차원이나 거리 메트릭으로 컬렉션을 생성하면 전체 데이터를 다시 색인해야 합니다. 이 과정은 임베딩 재생성(외부 API 비용 발생), 데이터 적재, HNSW 인덱스 빌드 세 단계가 모두 필요하므로 수백만 개 이상의 벡터에서는 수 시간 이상 걸릴 수 있습니다. 새 시스템에서는 전체 데이터의 1% 샘플로 먼저 설정을 검증한 뒤 전체 데이터를 적재하는 것을 강하게 권장합니다.

두 번째 함정은 **배치 업서트(batch upsert) 크기 설정**입니다. 한 번에 너무 많은 벡터를 전송하면 메모리 스파이크와 타임아웃이 발생합니다. 일반적으로 배치 크기 100~500이 안정적이며, 병렬 요청은 CPU 코어 수와 메모리를 고려해 2~4개 정도가 적절합니다. gRPC를 사용하면 REST보다 직렬화 오버헤드가 적어 대량 적재 시 유리합니다.

세 번째는 **벡터 ID 관리**입니다. Qdrant는 동일한 ID로 업서트하면 기존 벡터를 교체합니다. 이는 문서 업데이트를 구현하기 쉽게 해주지만, ID 생성 로직에 버그가 있으면 의도치 않게 데이터가 덮어씌워집니다. UUID v5(namespace + 문서 원본 ID)로 결정론적 ID를 생성하는 방식이 운영 환경에서 안전합니다.

```python
import uuid
from qdrant_client.models import PointStruct

NAMESPACE = uuid.UUID("6ba7b810-9dad-11d1-80b4-00c04fd430c8")  # URL namespace

def stable_id(doc_id: str) -> str:
    """문서 원본 ID를 결정론적 UUID v5로 변환 — 재적재 시 동일한 ID 보장"""
    return str(uuid.uuid5(NAMESPACE, doc_id))

def upsert_batch(docs: list[dict], vectors: list[list[float]]):
    points = [
        PointStruct(
            id=stable_id(doc["id"]),
            vector=vec,
            payload={
                "tenant_id":  doc["tenant_id"],   # 인덱스 필드
                "category":   doc["category"],
                "created_at": doc["created_at"],
                "title":      doc["title"],
                "source_url": doc["url"],          # 비인덱스 표시용 필드
            },
        )
        for doc, vec in zip(docs, vectors)
    ]
    # wait=True: 업서트 완료를 확인한 뒤 반환 (데이터 유실 방지)
    client.upsert(collection_name="documents", points=points, wait=True)
    # 결과: 배치 완료, 반환값은 UpdateResult(status='completed')
```

`wait=True`를 생략하면 비동기로 처리되어 응답이 빠르지만, 장애 발생 시 업서트가 실패했는지 확인할 방법이 없습니다. 운영 환경에서는 `wait=True`를 사용하거나, 비동기 방식을 선택할 경우 응답의 `operation_id`를 추적해 완료 상태를 검증하는 로직을 별도로 구현해야 합니다.

### 모니터링과 디버깅

검색 품질이 예상보다 낮을 때 가장 먼저 확인해야 할 것은 `hnsw_ef` 값입니다. 많은 경우 `hnsw_ef`가 `limit`보다 크지 않아 recall이 심각하게 낮아집니다. Qdrant의 REST API에서 `with_payload: false`, `with_vectors: false`로 설정하면 응답 크기를 줄여 레이턴시를 개선할 수 있습니다. 벡터가 필요 없는 경우에도 기본값으로 벡터를 포함하는 실수가 자주 발생합니다.

특정 필터 조건에서만 레이턴시가 높다면, 해당 조건의 인덱스 유무와 선택성을 확인합니다. `GET /collections/{name}/info` API는 컬렉션의 세그먼트 수, 인덱싱 상태, 최적화 진행 상황을 반환합니다. `indexed_vectors_count`가 `vectors_count`보다 현저히 낮으면 인덱스 빌드가 아직 진행 중이거나 optimizer가 지연되고 있다는 신호입니다. 이 상태에서 필터 쿼리를 실행하면 인덱스 없는 세그먼트는 순차 스캔으로 처리됩니다.

### 확장/마이그레이션

컬렉션 설정을 변경해야 하는 경우, Qdrant는 일부 변경은 온라인으로 지원하고 일부는 재생성이 필요합니다. **페이로드 인덱스 추가**는 온라인으로 가능하며, 백그라운드에서 기존 데이터에 대한 인덱스가 빌드됩니다. **양자화 설정 추가**도 온라인으로 변경할 수 있으며, optimizer가 백그라운드에서 기존 세그먼트에 양자화를 순차적으로 적용합니다. 반면 **벡터 파라미터(차원, 거리 메트릭) 변경**은 불가능하며 컬렉션을 새로 만들어야 합니다.

마이그레이션 전략으로는 **블루-그린 방식**이 안전합니다. 새 설정으로 컬렉션을 생성하고 기존 데이터를 전부 새 컬렉션에 적재한 뒤, 쿼리 트래픽을 점진적으로 전환합니다. 전환 기간 동안 쓰기 요청을 양쪽 컬렉션에 동시에 보내는 방식이 단순하고, 데이터 볼륨이 수천만 개 이상이라면 적재 완료 후 차이분만 동기화해 다운타임을 최소화합니다. Qdrant 1.9 이후 **named vectors** 기능을 활용하면 단일 컬렉션 안에 여러 임베딩 모델의 벡터를 함께 저장할 수 있어, 모델 마이그레이션 시 점진적 전환이 더욱 편리해졌습니다.

## 맺음말

### 핵심 요약

Qdrant를 운영 환경에서 성공적으로 운영하려면 세 가지 영역의 설계 결정이 조화를 이루어야 합니다. 첫째, **컬렉션 설계**에서는 벡터 차원·거리 메트릭·데이터 타입을 신중하게 선택하고, 필터링에 쓰일 모든 페이로드 필드에 적절한 인덱스를 생성해야 합니다. 차원과 거리 메트릭은 생성 후 변경할 수 없으므로 초기 설계가 이후 모든 운영 비용을 결정합니다. 둘째, **HNSW 튜닝**에서는 메모리 예산 안에서 `m`의 상한을 먼저 정하고, `ef_construct`는 `m`의 2~4배로 설정하며, 검색 시 `hnsw_ef`는 서비스 SLA에 따라 조정합니다. 셋째, **필터 최적화**에서는 모든 필터 필드에 인덱스를 생성하고, 선택성 높은 조건을 `must` 배열 앞에 배치합니다.

### 적용 판단 기준

Qdrant가 적합한 시스템은 벡터 검색이 핵심 워크로드이고, 데이터 거주 요건이 있거나 비용 통제가 중요하며, 수백만 개 이상의 벡터를 페이로드 필터와 함께 검색해야 하는 경우입니다. 기존에 Elasticsearch를 운영 중이고 벡터 검색 비중이 낮다면 Elasticsearch의 kNN을 먼저 시도하는 것이 운영 복잡도를 낮추는 선택입니다. 수억 개 이상의 벡터를 처리해야 한다면 Binary 양자화와 온디스크 인덱스를 조합해 메모리 비용을 수십 분의 일로 줄이는 방향을 검토할 가치가 있습니다. Qdrant 1.9 이후에는 **sparse vector** 지원이 안정화되어, 밀집 벡터와 희소 벡터를 함께 저장하는 하이브리드 검색 아키텍처도 단일 클러스터에서 운영할 수 있습니다. 처음에는 `float16` + Scalar 양자화 + `m=32` 조합으로 시작해 실제 트래픽 패턴을 관찰한 뒤 파라미터를 조정하는 접근이 가장 현실적입니다.
